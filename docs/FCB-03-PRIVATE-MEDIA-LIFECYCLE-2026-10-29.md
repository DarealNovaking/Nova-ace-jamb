# FCB-03 private question media — implementation contract (not applied)

Date: 29 October 2026. Status: **design/review boundary only; no Storage resources, provider credentials, signed links, server endpoints, schema changes, or question content created**.

This document is the next dependency after `supabase/proposals/fcb03_rich_content_validation.sql`, whose isolated database contract checks verify *shape*, not asset ownership. The existing `ace.question_media` and `ace.questions.media` columns must not be interpreted as usable upload permission. The existing text-only `manage_question` and `restore_question` must keep rejecting media until the complete implementation and tests are approved.

## Required server-side protocol

1. **Private intake:** provision one *private* Supabase Storage bucket with neither public reads nor client-selected paths. Accept only actual PNG/JPEG/WebP bytes after checking magic bytes, decoded dimensions, non-animation, safe re-encoding, and size (initial policy: at most 2 MiB and 4096×4096 pixels); forbid SVG/HTML/PDF/XML, external embeds, executable polyglots and untrusted remote image URLs. File extension and browser-supplied MIME are **not** authority. Enforce request size before buffering. Preserve SHA-256, trusted decoded MIME and immutable object path; strip unwanted metadata. If server-side image processing capabilities are unavailable, block activation rather than bypass checks.
2. **Authenticated draft-only staging:** server verifies an unexpired JWT and **current** `ace.roles` editorial role. It verifies the caller may edit the specific existing *private* question, the expected version matches, and the approved syllabus remains valid. Client supplies no bucket/path/key/owner override. Generate opaque asset ID and random immutable path on the server, with `question_id` and `content_version` binding. Require descriptive alt text (8–500 characters) and evidence of rights/ownership. Never let a student or anonymous user upload. For an initial new question, save a plain private draft first, then stage assets against its returned UUID and revision.
3. **Two-system failure handling:** Storage and Postgres cannot be rolled back atomically. Reserve a short-lived **pending** upload intent, write and verify the object under a new path, then mark the metadata **ready** through an authorization-checked database boundary. A failed reservation/write/confirmation never makes an asset publishable; retry idempotently using server-owned request ID; sweep only expired and unreferenced pending objects after a grace period. Never delete a referenced asset because a cleanup job guessed it was obsolete.
4. **Review and publication:** server validates all document blocks, every referenced asset belonging to the **same question and reviewed revision**, immutable SHA-256/object ID, verified bytes, approved usage rights and meaningful alt text. Different administrator reviews content and rights; editing bytes or document resets the review state. Publish only when all references are verified and full approval remains valid. Preserve immutable history/attempt snapshots; restoring older revisions makes a *new private draft* and must not reuse a deleted/stale/restricted asset.
5. **Student media delivery:** prefer an authenticated, bounded binary proxy that checks each request against owned attempt paper/question binding, published/rights-approved question and asset, and current withdrawal state, **before** streaming bytes. Return strict image type, `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store`, and a tight content-security policy. Do not return a permanent Storage object URL, Storage key, admin evidence, answer key, or explanation to student clients. Response should never reveal object existence across owners.
6. **Withdrawal and history:** withdrawing a question invalidates **future** media-delivery authorization; in-flight/cached bytes cannot be retroactively recalled, so do not promise that. Existing CBT attempt content remains cryptographically or referentially frozen for scoring; inaccessible images render the existing textual alt placeholder. Audited takedown must also stop active delivery when rights are withdrawn. Retain object versions while any approved history/audit/attempt snapshot references them; purge only by explicit retention policy and guarded reference checks.

## Explicit threats and acceptance tests

- Unauthenticated, student, unrelated editor, wrong owner, fabricated admin role, stale revision, withdrawn/published upload: **deny**.
- Misleading MIME, spoofed magic bytes, images exceeding encoded/decoded limits, decompression bombs, SVG/script/polyglot, file extensions, bypassed antivirus/re-encoding, path traversal: **deny**.
- Asset of another question, different revision, pending/unverified/rejected rights, missing alt text, asset replaced at same path, mutable history asset, leaked Storage URL: **deny**.
- Concurrent upload/review/withdraw/restore, duplicate request idempotency, transaction failure between Storage and DB, orphan sweep racing new references: verify in isolated PostgreSQL + mocked Storage.
- Owned active paper, non-public published question, expired/revoked tokens, withdrawal mid-download, browser error/no media, Android low bandwidth, keyboard/screen reader fallback: explicit E2E checks.

## Private image reservation and byte-verification implementation — 29 October 2026

- New proposal **`supabase/proposals/fcb03_media_intents.sql`** creates an RLS-enabled `ace.question_media_intents` staging table with **no client table privileges** and two trusted-server-only functions with **no anon/authenticated EXECUTE**. Reservation requires a current editor/admin role, private owned/current question revision (admin exception for editing), bounded image metadata, rights evidence, unique server-generated opaque object path, 15-minute expiry, four-live-intents-per-question/revision limit and identical-request replay. Confirmation rechecks actor, ownership, revision and asserted SHA-256/MIME/size before marking **metadata only** as verified. Both paths share the existing question-authoring advisory lock and question-row lock. The reservation's SHA/size/MIME are *claimed*, not sufficient to trust actual bytes.
- New reusable **`supabase/functions/_shared/questionMedia.ts`** is a backend-only, fail-closed protocol. It requires a **supplied real safe decoder/re-encoder** (not yet integrated); format/magic-byte agreement, at most 2 MiB, single frame, bounded decoded dimensions, SHA-256 of sanitized bytes and immutable storage write/readback SHA-256 match before database confirmation. No public URLs, bucket, live endpoint, media publication or automatic file cleanup. Without a real sanitizer/storage adapter this helper cannot upload an actual image.
