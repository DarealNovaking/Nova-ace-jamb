# FCB-03 question workflow

Continue the approved FCB-03 scope from the master handoff. Reuse `ace.questions`, `question_versions`, the existing admin review queue and authenticated Supabase client. The bank, history, media and source tables are empty in the live read-only inventory. There are no client table grants, no question mutation guards, and no authoring RPC. The existing queue is read-only.

Use narrowly scoped RPCs rather than restoring broad table access or adding a separate backend. Authors may save private drafts and submit; a different administrator must approve/reject. Administrators publish and withdraw. A content edit invalidates approval. All successful mutations require an expected revision, append an immutable snapshot and audit event in the same transaction, and preserve stable IDs. Do not expose answer keys through student table access. Match published subject/topic/subtopic ancestry and season; validate four nonempty, distinct options, a valid answer, explanation, difficulty, original/source evidence and bounds. Normalize content for duplicate detection, serialize competing mutations, and refuse stale role/row snapshots.

This first implementation accepts plain text, including Unicode mathematical notation, without HTML execution. It must reject unsupported embedded media rather than silently publish it. Structured rich content, private media upload/delivery, import, moderation and an independently reviewed lawful first dataset remain separate FCB-03 acceptance tasks. No invented JAMB past questions or source rights. Do not deploy or mutate production until a concrete reviewed release is authorized.

The owner has delegated routine implementation choices and asked to proceed without repeated design questions. The engineering choice is the existing RPC/schema architecture with two-person approval; no new dependencies. Alternatives rejected: direct table CRUD cannot enforce lifecycle/immutable audit safely; a new service duplicates the existing authorization stack.
